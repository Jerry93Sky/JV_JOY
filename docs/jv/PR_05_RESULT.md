# PR_05 — результат: JV-Line BOM и материальная себестоимость

## Итог

PR_05 расширил JV-Line BOM с 14 до 26 строк и уменьшил неподдержанную часть каталога с 26 до 14 строк при наличии всех необходимых входов. Добавлен независимый расчёт стоимости поддерживаемых позиций для профилей `COMPLETATION` и `RETAIL`. Результат остаётся частичной спецификацией и частичной суммой материалов; коммерческая цена конструкции не рассчитывается.

Исходные книги не изменялись. Excel 16.0 пересчитывал временные копии при выключенных макросах и событиях. Оригиналы соответствуют SHA-256 `62dd6d49…d2d8` (комплектация) и `025d7e29…ab41` (розница).

Для LN-T90/LN-B90 нужны `L1!D8`; для LN-230 и LN-240 нужны фактические значения `L1!D19`/`D20`. Без этих необязательных для текущего вызова полей функция не подставляет нули и оставляет соответствующие позиции неподдержанными. Без входов для LN-040 остаётся неподдержанной и эта строка.

## Числовая точность и Excel

`L1!O5` задана формулой `=$D$32/1000+Настройки!$D$7/1000`. Для случая с двумя сторонами пересчитанная книга даёт `D32=5438`, `Настройки!D7=100`, следовательно десятичный результат движка — `5.538`. Свежий Excel `Value2` возвратил `5.538`, IEEE-754 bits `401626E978D4FDF3`, формат `0,000` и текст `5,538`. Для сценария большой створки аналогично получены `6.405`, bits `40199EB851EB851E`, формат `0,000`, отображение `6,405`.

Ранее сохранённая PR_04 выборка содержала текст `5.537999999999999`/`6.404999999999999`. В нескольких свежих `CalculateFullRebuild` это отличие не воспроизвелось: двоичные биты, десятичный COM round-trip и отображение теперь согласованы с ближайшим binary64 для точного десятичного результата. Исторические строки не переписывались в качестве входов движка и не использовались для подгонки. Новые фикстуры сохраняют COM `Value2`, битовый шаблон, отображение и `NumberFormat`.

По 260 поддержанным количествам: 240 `EXACT` относительно точного рационального значения Excel binary64, 20 `NUMERICALLY_EQUIVALENT` по отображению ячейки (три знака после запятой), 0 `MISMATCH`, 0 `UNVERIFIED`. По 260 суммам строк `Q`: 181 `EXACT`, 79 совпадают по отображению денежной ячейки с двумя знаками, 0 расхождений и 0 непроверенных. Это не доказывает равенство неокруглённых Excel double и рациональной суммы движка. Точные значения обеих сторон сохранены.

Отдельная проверка всех строк П/Q двух книг охватывает 800 результатов (40 строк × P и Q × 10 комбинаций книга/сценарий): 427 `EXACT`, 373 `NUMERICALLY_EQUIVALENT` по форматированию, 0 `MISMATCH`, 0 `UNVERIFIED`. Сравнение `NUMERICALLY_EQUIVALENT` использует исключительно отображаемую точность исходной ячейки и не меняет расчётное значение.

## Реализованная модель стоимости

- Цены E из `Прайс-Line` извлечены в отдельные snapshot-наборы для обеих книг; общий каталог количества не содержит цен. Снимки версионированы хешем исходной книги. Имя файла задаёт дату снимка `08.10.2026`; дата начала действия цены отдельно не подтверждена.
- Единицы сверяются с единицами строки BOM. Валюта подтверждена заголовками `L1!P4` и `L1!Q4` (`руб.`). Заголовок источника `Прайс-Line!E3` сохранён как `CC`; его полная семантика не подтверждена.
- `P5:P8` делят соответствующую цену источника на `Настройки!D2`. `P9:P43` используют цену источника напрямую с учётом сдвига каталожных строк для L1 строк 26–43. `P44` делит цену `Прайс-Line!E45` на `Настройки!L7`. Во всех строках `Q=P*O`.
- Умножение и деление стоимости выполняются точными рациональными `BigInt` значениями. Например, `4857.5 / 0.9` хранится как `48575/9`, не округляется до денежного decimal и не переводится в JS `Number`. Сумма поддержанных строк также остаётся точной рациональной дробью.
- Trace стоимости содержит строку, количество, формулу `L1!P`, workbook/профиль и версию snapshot. Неподдержанные позиции возвращаются отдельно. Частичное значение обозначено `PARTIAL_SUPPORTED_POSITIONS`/`supportedSubtotal`.

## Проверки и файлы

- Пересчитано 5 входных сценариев в обеих книгах: 10 прогонов. BOM количества и геометрия совпали с новыми результатами Excel во всех 10 прогонах; сравнение без epsilon, десятичными BigInt значениями.
- По 260 quantity и 260 amount строк выполнен отдельный parity-анализ с IEEE bits и форматами; результаты в `LINE_MATERIAL_PARITY.json`.
- Все 800 ценовых ячеек проверены в `LINE_PRICE_PARITY.json`.
- Snapshot цены: `fixtures/line-price-snapshots.json`; Excel COM-фикстура: `fixtures/line-price-excel-golden.json`.
- Полный `pnpm --filter @bms/shared test:jv` — 40 passed, 0 failed. `pnpm dlx --package typescript@5.9.3 tsc -p packages/shared/tsconfig.jv.json` — passed. Дополнительные parity-команды и Excel run приведены в `LINE_MATERIAL_TEST_REPORT.md`.

## Что пока не рассчитано

Не поддержаны 14 строк: LN-020, LN-030, LN-070-A/B/C, LN-080, LN-090, LN-100, LN-110, LN-120, LN-130, LN-190, LN-200, AA-010. Главная ветка — створочные профили `F33:F39` и их зависимые геометрические ячейки; парковочные защёлки используют validation-состояние и матрицы ПД. Исходные матрицы ПД уже импортированы, но эту связанную последовательность нельзя считать полностью подтверждённой только фактом наличия таблиц.

В Excel Q52 суммирует Q5:Q50, то есть включает дополнительные строки AA-020/050/070/090/110/120 (L1!O45:O50), которых нет в базовом каталоге 40 строк PR_04. Q53:Q58 включают покраску, работы/сборку, монтаж, внешние прайсы и error guard. Формула L1!Q58 разобрана статически и сохранена в `LINE_PRICE_RULES.md`, но не перенесена; поэтому engine `supportedSubtotal` намеренно не сравнивается с Q52/Q58 и не называется итоговой себестоимостью.

Цена покраски `V`, масса `S`, стекло, услуги, монтаж, скидки, наценки и итоги конструкции не включены в subtotal. Наценка, продажная цена и себестоимость не смешиваются. Проверка Excel касается заданных 5 сценариев, а не полного пространства размеров и переключателей.

Существующий `/calculate`, Prisma schema, React и legacy BMS алгоритмы не менялись. Новая подсистема находится в `packages/shared/src/jv` и не подключена к рабочему API.
