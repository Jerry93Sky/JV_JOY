# JV-Line: расчёт раскроя несущего профиля

## Источник и назначение

Проверены обе книги от 08.10.2026. Формулы в `L1!C28:D32`, `L1!O5` и необходимые ссылки одинаковы. Размеры и подписи указывают, что строки A/B/E/F — четыре отреза несущего профиля; единица настроек в `Настройки!P1` — `мм`. Это схема длин отрезов, а не задача оптимизации раскладки по стандартным хлыстам: в этом блоке нет длины хлыста, карты резов, отхода или алгоритма nesting.

## Формулы и зависимости

| Excel | Формула/значение | Входы | Результат |
|---|---|---|---|
| `L1!C28` | `=$D$6` | D6 | Количество A-отрезов |
| `L1!D28` | `=$I$26+Настройки!$P$2/2` | I26, P2 | A-рез, «глубина парковки» |
| `L1!C29` | `=$D$6` | D6 | Количество B-отрезов |
| `L1!D29` | `=$I$27+Настройки!$P$2/2-Настройки!$P$7` | I27, P2, P7 | B-рез, «ширина парковки» |
| `L1!C30` | `=$D$6` | D6 | Количество E-отрезов |
| `L1!D30` | `=$I$26-Настройки!$P$6/2` | I26, P6 | E-рез, «глубина парковки на линии остекления» |
| `L1!C31` | константа `1` (не формула) | — | Единственный F-отрез |
| `L1!D31` | `=$D$3-$D$6*(Настройки!$P$6+$D$30)` | D3, D6, P6, D30 | F-рез, основная часть несущего профиля |
| `L1!D32` | `=$C$28*$D$28+$C$29*$D$29+$C$30*$D$30+$C$31*$D$31` | все четыре количества и длины | Суммарная длина отрезов в исходной единице длины |
| `L1!O5` | `=$D$32/1000+Настройки!$D$7/1000` | D32, Настройки D7 | Количество профиля для строки материала, погонные метры |

Настройки: `P2=Ширина несущего профиля`, `P6=Ширина тройника`, `P7=Вылет хобота тройника (от оси)` (подписи в O2/O6/O7; общий индикатор единиц — P1=`мм`). Для `Настройки!D7` подпись C7 — «Припуск для несущего Line», а `E7` явно указывает `мм`. Здесь нет ROUND/ROUNDUP/ROUNDDOWN/INT. Деление P2/2 и P6/2, умножение количества на длину и `/1000` выполнены без округления десятичной арифметикой BigInt.

## Граф

```text
Главная!C11 -> L1!D3 ------------------------------------------┐
Главная!L11 -> CEILING(...,1) -> L1!D5 -> I25 -> I27 -> D29  │
Главная!J11 -> K11 -> L1!D6 ───────────────> C28/C29/C30     │
                                         ├─ I25/I26          │
L1!C23/C24 -> D23 -> PD INDEX -> O15 -> I26 ─> D28, D30      │
Настройки!P2 ────────────────────────────────> D28, D29       │
Настройки!P7 ───────────────────────────────────> D29        │
Настройки!P6 ───────────────────────────────────> D30 -> D31 │
Все C28:D31 ───────────────────────────────────────────────> D32
D32 + Настройки!D7; /1000 ──────────────────────────────────> O5
L1!L5/M5/N5 -> Прайс-Line!B5/C5/D5 (код/имя/единица LN-010)
O5 -> Q5 (стоимость), S5 (вес), V5 (покраска); цены не реализуются здесь.
```

Скрытая деталь: количество створок D5 влияет на расчёт длин через уже реализованные I25/I26 и таблицу ПД, но напрямую не участвует в C28:C31. Количества резов A/B/E используют D6. `L1!D6=IF(Главная!K11<=2,Главная!K11,"НЕТ")`; `Главная!K11=IF(Главная!J11<=2,1,Главная!J11-1)`. Входы геометрии повторно не вычисляются: `calculateLineGeometryAndCuts` передаёт I26/I27 из существующих JV-Line правил в cutting DAG.

## Материал и граница спецификации

Ячейки `L1!L5/M5/N5` ссылаются на `Прайс-Line!B5/C5/D5`. В обеих книгах это `LN-010`, «Профиль несущий», `п.м`. Поэтому выход содержит четыре отдельные записи длины/количества резов, суммарный метраж D32 и формульное количество `O5` для будущей спецификации. Розничные и комплектационные цены строки (значения E5 и формула P5/Q5), коэффициент раскроя `Настройки!D2`, стоимость CC, вес и покраска остаются вне этого модуля.

`apps/backend/src/prisma/import-formulas.ts` содержит прежнее упрощённое правило LN-010 `round((width + 100) / 1000 / cutCoeff, 3)`. Его структура не совпадает с Excel-путём: Excel суммирует четыре геометрически обусловленных отреза в D32, добавляет припуск D7 и только затем переводит в метры. Для тестового входа width=4000 legacy выражение с `cutCoeff=0.9` даёт 4.556 м после округления, а пересчитанный Excel O5 даёт 4.877 м. Legacy формула не менялась и не используется новым кодом.

## Ограничения единиц и точности

Параметры P2/P6/P7 и припуск D7 явно обозначены в миллиметрах. Excel не показывает единицу прямо рядом с `Главная!C11` / `L1!D3`, хотя вычисления смешивают D3 с миллиметровыми настройками; вызывающая сторона обязана указать одну общую единицу, API отклоняет смешение unit labels. Golden scenarios использовали `mm` и подтверждают этот источник целевой книги, но не исправляют отсутствие подписи в исходном input sheet.

Формульные значения и математика сверены для пяти сценариев, двух книг; это выборочное подтверждение этих веток. Оно не доказывает parity для всех возможных значений, ошибок Excel, полного BOM или цены.
