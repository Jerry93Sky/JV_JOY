## 3. Главная цель R4.2

Превратить сохранённые JV-заказы в полноценные рабочие черновики.

Пользователь должен иметь возможность:

1. Создать заказ.
2. Редактировать конструкции.
3. Не нажимать «Сохранить» после каждого изменения.
4. Закрыть страницу и открыть заказ позднее.
5. Восстановить сохранённые изменения.
6. Посмотреть предыдущие версии.
7. Восстановить предыдущую ревизию.
8. Создать шаблон конструкции.
9. Применить шаблон в другом заказе.
10. Не потерять данные при конфликте между двумя вкладками.

**Не переписывай калькулятор. Используй существующий JV Workspace и backend R4.1.**

## 4. Автосохранение

Реализуй надёжное debounced autosave.

### Требования

- После изменения заказа автоматически сохранять черновик.
- Использовать разумную задержку после последнего изменения, ориентировочно 1–2 секунды.
- Не отправлять запрос после каждого нажатия клавиши.
- Показывать статус «Есть изменения», «Сохранение…», «Сохранено» или «Ошибка сохранения».
- Сохранить возможность ручного сохранения.
- Не создавать несколько одинаковых заказов из-за повторных запросов.
- Не запускать автосохранение при первоначальной загрузке заказа без изменений.
- Не создавать новую ревизию при неизменившихся данных.

Для нового заказа обеспечь безопасное автоматическое создание серверного черновика. Предусмотри защиту от дублирования при повторной отправке запроса.

### Важные сценарии

Проверь:

- Быстрое изменение нескольких полей.
- Сохранение при переключении конструкций.
- Изменение ценового профиля.
- Изменение порядка конструкций.
- Undo/Redo.
- Медленный ответ backend.
- Ошибку сети.
- Обновление страницы во время сохранения.
- Выход из редактора при несохранённых изменениях.

Не очищай форму после неуспешного сохранения.

Не показывай «Сохранено» до подтверждения сервера.

Не используй `beforeunload` как единственный механизм сохранения.

## 5. Конфликты между вкладками

Существующий R4.1 возвращает HTTP 409 при конфликте версий.

Сохрани это правило.

Добавь понятное поведение интерфейса:

- Сообщение «Заказ изменён в другой вкладке».
- Возможность открыть актуальную серверную версию.
- Возможность сохранить локальные изменения отдельно, если это безопасно.
- Предупреждение о риске потери данных.
- Отсутствие автоматической перезаписи чужих изменений.

Не реализуй молчаливый last-write-wins.

Сериализуй сохранения одного заказа, чтобы более старый запрос не перезаписывал более новый черновик.

## 6. История изменений и восстановление ревизий

Сейчас сервер хранит `JvOrderRevision`.

Расширь интерфейс истории:

- Номер версии.
- Дата и время.
- Автор.
- Возможность посмотреть сохранённые параметры.
- Возможность выбрать предыдущую версию.
- Предпросмотр того, что будет восстановлено.

Добавь действие:

**«Восстановить эту версию»**

Восстановление должно:

1. Прочитать выбранную ревизию.
2. Проверить доступ пользователя.
3. Показать подтверждение.
4. Применить сохранённые параметры.
5. Создать **новую ревизию**, а не уничтожить существующую историю.
6. Сохранить правильные слоты, профили и конфигурации.
7. Сбросить устаревший результат расчёта.

Проверяй версию заказа перед восстановлением; при конфликте возвращай 409.

Не позволяй откатить заказ через незащищённую прямую замену JSON.

## 7. Шаблоны конструкций

Добавь возможность создавать шаблоны на основе существующих конфигураций JV.

Минимальный функционал:

- Сохранить конструкцию как шаблон.
- Задать понятное название.
- Просмотреть список шаблонов.
- Выбрать шаблон.
- Добавить конструкцию из шаблона в текущий заказ.
- Изменить название шаблона.
- Удалить шаблон с подтверждением.

Шаблон должен хранить:

- Семейство конструкции.
- Входные параметры.
- Количество, если применимо.
- Конфигурацию.
- Версию правил и UI-схемы.
- Автора.
- Дату создания и изменения.

Шаблоны не должны хранить текущую коммерческую цену как гарантированную для будущего заказа.

Особое внимание удели Front с дверью.

Если шаблон применим только к фиксированному набору семи конструкций, поддержи его как шаблон целого заказа либо явно запрети некорректное применение как одиночной позиции.

Не придумывай новые поддерживаемые конфигурации Front.

Используй серверную валидацию и действующие роли OWNER/ADMIN.

## 8. Версии расчёта и ценового профиля

R4.1 уже сохраняет `uiSchemaVersion`, `rulesVersion` и `profile`.

Сохрани эти данные при автосохранении, создании шаблонов и восстановлении ревизий.

При повторном открытии старого заказа:

- Показывай, какие версии использовались.
- Отмечай потенциальную несовместимость с текущими правилами.
- Не заменяй исторические входные параметры автоматически.
- Не показывай устаревшую цену как текущую.
- Предлагай выполнить новый расчёт.

Не создавай неподтверждённые коммерческие snapshots.

Полноценная фиксация цен для коммерческих документов относится к последующим R5/R6.

## 9. PostgreSQL и API

Используй существующие модели `JvOrder` и `JvOrderRevision`.

Расширяй Prisma schema только там, где действительно требуется.

Новые шаблоны храни в PostgreSQL, а не исключительно в localStorage.

Для автосохранения используй действующую архитектуру JV Orders API.

Добавь API для:

- Шаблонов.
- Получения выбранной ревизии, если текущих маршрутов недостаточно.
- Безопасного восстановления ревизии.
- Идемпотентного создания нового черновика, если это требуется.

Проверь авторизацию и ограничения доступа.

Все изменения заказа и его истории должны оставаться транзакционными.

## 10. Обязательные тесты

Используй отдельную PostgreSQL, а не демонстрационную базу.

Проверь:

- Создание и автосохранение нового заказа.
- Автосохранение существующего заказа.
- Быстрые последовательные изменения.
- Отсутствие лишних ревизий.
- Повторное открытие после перезагрузки.
- Две одновременно открытые вкладки.
- Конфликт HTTP 409.
- Потерю сети и повтор сохранения.
- Историю ревизий.
- Восстановление старой ревизии как новой.
- Шаблоны всех поддерживаемых семейств.
- Front с дверью.
- COMPLETE/PARTIAL.
- Оба ценовых профиля.
- Недостаточные права.
- Отсутствие устаревшей цены после открытия или восстановления.

Проверь, что Undo/Redo не теряют данные из-за асинхронного сохранения.

После интеграционных тестов проверь очистку временной БД.

Запусти существующую JV-регрессию, backend/frontend builds, shared typecheck, API, browser E2E и fixtures.

Excel-эталоны и формулы не изменять.
