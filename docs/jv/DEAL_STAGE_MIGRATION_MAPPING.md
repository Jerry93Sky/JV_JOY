## Important limitation in the migration

The SQL migration maps non-lead `CALCULATION` and `PROPOSAL` to `ASSEMBLY`, which is also the live post-payment assembly stage. It drops the original stage value and does not create a history event or separate proposal-status field. `CommercialProposal` can prove that proposal versions exist, but cannot prove that every migrated `ASSEMBLY` row is still pre-invoice or whether it came from `CALCULATION` versus `PROPOSAL`. PR_14C does not treat `ASSEMBLY` as a proposal state or add a schema discriminator. Existing migrated rows with this ambiguity need product/data-owner direction before an automated backfill or broader transition is safe.

## Current transition contract

- Proposal versions are created only while the deal is `IN_PROGRESS`. Multiple versions are allowed, numbered from the persisted proposal count. The route does not mutate the deal stage.
- First invoice requires at least one proposal and stage `IN_PROGRESS`. It performs the existing bundle reservation calculation, sets `INVOICE_SENT`, `paymentType`, placeholder `invoiceUrl`, and `invoiceSentAt`, then logs the existing stage event. If a go-back returns a deal to `IN_PROGRESS` but keeps its original `invoiceSentAt`, a subsequent invoice call skips reservation.
- Invoice reissue is accepted while stage is `INVOICE_SENT`, preserves the existing `invoiceSentAt`, updates the same invoice fields, and skips inventory reservation.
- Partial/full payment remains permitted for `INVOICE_SENT` and partial-payment recovery. Partial payment leaves the stage unchanged; full payment sets `PAID` and logs the existing payment and stage events.
- Deal endpoints still use `requireAuth`; no new role restriction was inferred or added. The JWT-authenticated `USER` path remains permitted by this middleware contract.
