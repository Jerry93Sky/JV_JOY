# Как проверить актуальную тестовую сборку JV_JOY

**Последняя проверенная тестовая версия находится в `main`.** В неё входят R5.7 со связью выпущенного КП и сделки и R5.8 с проектом счёта. **Тестовая сборка — не для самостоятельного коммерческого выпуска без контроля.**

Если репозиторий уже клонирован, обновите чистую локальную ветку через `git fetch origin main`, `git switch main` и `git merge --ff-only origin/main`. Версия подтверждается успешным запуском Actions на точном SHA.

## Подготовка и запуск на Windows

Понадобятся Git, Node 24.13.0, pnpm 11.25.0 и Docker с Docker Compose для локальной PostgreSQL. Можно использовать отдельную PostgreSQL 16 без Docker. Исходные Excel-книги для запуска программы и тестов из репозитория не требуются.

1. Клонируйте репозиторий и установите зависимости.

   ```powershell
   git clone --branch main https://github.com/Jerry93Sky/JV_JOY.git
   cd JV_JOY
   pnpm install --frozen-lockfile
   ```

2. Запустите изолированную БД. Пример создаёт отдельный Docker-проект `jv-joy-testing` с собственным томом. Если порт 55432 занят, выберите другой и используйте его во всех командах ниже.

   ```powershell
   $env:JV_TEST_DB_PORT = '55432'
   $env:JV_TEST_DB_PASSWORD = [guid]::NewGuid().ToString('N')
   docker compose -f compose.testing.yml up -d --wait
   $env:DATABASE_URL = "postgresql://jvtester:$($env:JV_TEST_DB_PASSWORD)@127.0.0.1:$($env:JV_TEST_DB_PORT)/jvjoy_testing"
   $env:JWT_SECRET = [guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')
   $env:ADMIN_INITIAL_PASSWORD = Read-Host 'Задайте пароль для тестового пользователя admin'
   ```

   Сохраните пароль тестовой БД и пароль `admin` у себя. При следующем запуске с тем же томом укажите прежний пароль PostgreSQL и прежний пароль `admin`. Параметры этой инструкции относятся только к тестовой базе. При использовании своей тестовой PostgreSQL задайте адрес через `DATABASE_URL`, а ключ JWT и пароль владельца задайте так же.

3. В этом же терминале создайте клиент Prisma, примените миграции, создайте начального пользователя и запустите API.

   ```powershell
   pnpm --filter backend db:generate
   pnpm --filter backend exec prisma migrate deploy
   pnpm db:seed
   New-Item -ItemType Directory -Force apps/frontend/dist | Out-Null
   pnpm dev:backend
   ```

   Seed создаёт `admin` с ролью владельца, если пользователя ещё нет. Backend слушает порт 3001.

4. В другом терминале из корня проекта запустите frontend.

   ```powershell
   pnpm dev:frontend
   ```

   Откройте [JV Workspace](http://localhost:5173/jv/orders/new) и войдите как `admin`. Vite проксирует `/api` на порт 3001. Для сценария JV-заказов, КП и проекта счёта дополнительных сервисов не требуется.

## Сценарий для приёмки

1. Создайте тестовый контакт и сделку. В JV Workspace выберите сделку, нажмите «Загрузить проверенный заказ без стекла» и дождитесь автосохранения. После перезагрузки откройте заказ через «Список заказов». Проверьте историю и сохранение шаблона.
2. Нажмите «Рассчитать». Для проверенного состава ожидается `COMPLETE`. Зафиксируйте расчёт, создайте черновик КП, заполните пять условий, сохраните их новой версией и передайте на согласование.
3. Согласуйте КП владельцем. Выпустите его из раздела «Выпуск КП». Для проверки инженера создайте отдельного пользователя с этой ролью в «Настройки → Пользователи» и войдите под ним в другом профиле Chrome.
4. В исходной сделке откройте «Выпущенные КП JV». Откройте клиентскую печатную форму и подготовьте проект счёта. Заполните тестовые реквизиты, сохраните, повторно откройте из сделки и проверьте PDF с отметкой «ПРОЕКТ — НЕ ВЫСТАВЛЕН».
5. Измените размеры в проверенном составе так, чтобы расчёт вернул `PARTIAL`. Например, задайте ширину первой конструкции 4001 мм. Убедитесь, что итог не подтверждён, а сохранить расчёт как подтверждённый снимок нельзя.

## Что учитывать

- Подтверждены отдельные конфигурации из двух книг Excel. Полного покрытия всех комбинаций пока нет. Некоторые заказы возвращают `PARTIAL`.
- Выпуск КП доступен только по согласованной сохранённой версии с подтверждённой суммой. Проект счёта хранится отдельно. Автоматизированное выставление, оплата и складской процесс для JV ещё разрабатываются.
- Этапы R6–R8 включают прайсы, эксплуатационные и нагрузочные проверки, пилот и релиз. Демонстрационный Docker может использовать более раннюю версию.
- Известные ограничения описаны в [дорожной карте](../../ROADMAP.md), [отчёте о parity для расчёта без стекла](GLASS_OFF_PARITY_RESULT.md), [бэклоге UX](FINAL_UX_BACKLOG.md) и [результате R5.8](R5_8_RESULT.md).

Когда закончите проверку, остановите тестовую PostgreSQL командой `docker compose -f compose.testing.yml stop`. Тестовые записи останутся в отдельном томе.

## Ветки для дальнейшей разработки

Создавайте короткую ветку из актуального `main`. Собирайте один логический набор изменений в одном PR. Перед объединением проверьте затронутые сценарии и CI на коммите PR. Незавершённую работу храните в отдельной ветке. [Обязательные проверки и Auto-merge](MAIN_AUTOMATION.md)

## Скачать проверенную сборку

1. Выберите успешный запуск **push** для `main` и скачайте `jv-main-<SHA>` в разделе **Artifacts**. Сверьте `build-info.json` и `verification.json` с SHA запуска. В артефакте есть готовые каталоги `apps/frontend/dist`, `apps/backend/dist/apps/backend/src` и `packages/shared/dist`. [Запуски GitHub Actions для main](https://github.com/Jerry93Sky/JV_JOY/actions/workflows/jv-ci.yml?query=branch%3Amain+event%3Apush)
2. Создайте чистое рабочее дерево из того же SHA, например `git worktree add --detach ../JV_JOY_checked <SHA>`. Выполните шаги подготовки зависимостей и отдельной PostgreSQL из этой инструкции. Для запуска артефакта нужны зависимости и сгенерированный Prisma Client из того же checkout.
3. Распакуйте архив и перенесите его каталоги `apps` и `packages` с сохранением относительных путей в это дерево. Запустите `pnpm --filter backend start` из корня после миграций и seed. Backend раздаёт собранный frontend на [localhost:3001](http://localhost:3001/jv/orders/new).
4. Для запуска из исходников версия определяется через `git rev-parse HEAD` в рабочем дереве запущенного процесса. Для артефакта проверьте метаданные по [build-info.json на работающем backend](http://localhost:3001/build-info.json). Там же указаны дата сборки и миграции этой версии.

## Совместимость PostgreSQL и возврат к предыдущей сборке

Перед запуском на отдельной базе выполните `pnpm --filter backend exec prisma migrate status` из checkout того же SHA. Сравните список миграций с `build-info.json`. Для проверки фактической структуры используйте read-only diff.

```powershell
pnpm --filter backend exec prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --exit-code
```

Код 0 означает отсутствие найденных различий, 2 — есть расхождения, 1 — проверка завершилась ошибкой. Расхождения разбирайте перед запуском. Если нужен откат, выберите предыдущий успешный SHA и откройте его в отдельном worktree. Используйте совместимую тестовую PostgreSQL или сначала восстановите резервную копию в отдельную базу и проверьте её. Сохраните текущую базу и том. Действующий демонстрационный стенд обновляется отдельно.
