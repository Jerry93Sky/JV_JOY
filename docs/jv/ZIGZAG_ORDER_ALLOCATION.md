# Zigzag: распределение общих расходов заказа

Лист `Клей+акт` выбирает расход материала по системному селектору каждой позиции заказа:

- `C5:C11 = Главная!G11:G17`; `C18:C24` использует те же селекторы.
- `Lrow=IFERROR(INDEX(Erow:Krow,Crow),0)`.
- `Mrow=Главная!Z[slot]`.
- `Nrow=IFERROR(Lrow*Mrow,0)`.
- Для selector `2` столбец F связан с `'Z1'..'Z7'!N34` (активатор) и N35 (клей). Это подтверждено формулами для всех слотов на временных копиях Excel.

Итоговые упаковки и коэффициенты — на весь заказ:

```text
N12 = MAX(1, ROUNDUP(SUM(N5:N11), 0))
O5  = N12 / SUM(N5:N11)
N25 = MAX(1, ROUNDUP(SUM(N18:N24), 0))
O18 = N25 / SUM(N18:N24)
```

Движок считает сумму точными рациональными величинами и округляет расход вверх до целого числа упаковок согласно исходной `ROUNDUP`. Коэффициент не вычисляется отдельно по конструкции. Если суммарный расход нулевой, Excel O5/O18 делит на ноль; движок возвращает typed error, а не придумывает коэффициент.

Распределение общей площади связано с `ПРМ!AB25:AB31`:

```text
Wslot = (ширина × высота × количество позиции) / SUM(площадь × количество по заказу) / количество позиции
```

Для ненулевого количества множитель сокращается математически до `ширина × высота / SUM(площадь × количество)`. Для количества 0 исходный `IFERROR(...,0)` даёт W=0. Все промежуточные операции рациональные.

PR_10G добавляет независимую оркестрацию полного Zigzag-заказа: геометрия и BOM каждой позиции → единые `N12/N25/O5/O18` и доли `AB/W` → индивидуальные P38:P44 → `Главная!Sslot=P44/Настройки!D12` → цена позиции по количеству. Минимальная упаковка применяется один раз на заказ, а не к каждой позиции. Шесть валидных двухпозиционных заказов (две книги × минимальный, активное стекло/C8=4 и расход 4 упаковок) закрывают полный путь; два дополнительных сценария сохраняют активную ошибку стекла как PARTIAL.

В исходной книге не подтверждена отдельная ячейка общей суммы заказа. Для независимой проверки сумма на временной копии Excel вычислялась контрольной формулой `=S11*Z11+S12*Z12` в `Главная!ZZ100`; ячейка не записывается в оригинал и не выдаётся за исходную формулу. Engine суммирует точные рациональные `unitSalePrice × quantity`. См. подробные формулы, Value2, двоичные значения, форматирование и trace в `ZIGZAG_ORDER_PR10G_PARITY.json`.

Наличие другого семейства оставляет заказ `PARTIAL`: его входы в N12/N25 неизвестны, поэтому общие коэффициенты для Zigzag нельзя считать окончательными. Точные требования к переходу смешанного заказа в COMPLETE перечислены в `PR_10G_RESULT.md` (раздел PR_10H).

Сравнения `Клей+акт!N12/N25/O5/O18`, `Z1/Z2!W5`, P34/P35 и P38 приведены в `ZIGZAG_PRICE_PARITY.json`.
