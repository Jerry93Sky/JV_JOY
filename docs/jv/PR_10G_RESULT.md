# PR_10G — расчёт коммерческого заказа JV-Zigzag

## Итог реализации

Добавлен экспортируемый `calculateZigzagOrder` в `packages/shared/src/jv/zigzag/order-calculation.ts`. Он принимает список позиций заказа, запускает существующие геометрию, BOM и прайс-калькуляторы, один раз считает общие клеевые коэффициенты и распределение площади, после чего рассчитывает P38:P44 для каждой Zigzag-позиции.

Для каждого слота рассчитывается единичная цена по подтверждённой формуле `Главная!Sslot = Zslot!P44 / Настройки!D12`. Стоимость позиции с количеством — точное произведение единичной цены и количества. Общая цена — точная сумма стоимостей позиций. Исходные книги не содержат подтверждённой отдельной ячейки общей суммы, поэтому на временных копиях использована контрольная Excel формула `=S11*Z11+S12*Z12` в `Главная!ZZ100`; это не заявляется как исходная формула. Excel возвращает конечный контрольный результат для сравнения.

`F28`, `Настройки!D32/D33/D34/L3` валидируются как настройки уровня заказа и не могут различаться между позициями одного workbook. `C8`, геометрия, количество, стекло и ручные N40/N41 остаются на уровне позиции.

## Подтверждённые цепочки

| Ветвь | Ячейки/формула | Результат |
|---|---|---|
| Заказный клей/активатор | `Клей+акт!N12/N25 = MAX(1,ROUNDUP(SUM(...),0))`; `O5=N12/SUM(N5:N11)`, `O18=N25/SUM(N18:N24)` | Одна общая упаковочная поправка на заказ, без повторения минимальной упаковки по каждой конструкции |
| Распределение площади | `ПРМ!AA25:AA31=ширина×высота×количество/1 000 000`; `AA32=SUM(AA25:AA31)`; `ABslot=AArow/(AA32×Wrow)`; `Z1!W5=ПРМ!AB25` | W рассчитан по площади позиции относительно площади всего заказа и подтверждён на двух слотах |
| Ручная ветвь C8=4 | `U10=N10×G10`; `U11=N40×G39`; `U12=N41×G40`; `U13=SUM(U5:U12)×IF(C8=4,L11,1)`; `U14=L9×L10×W5`; `U15=MAX(U10:U14)`; `U17=C24×W5`; `U18=U15+U17`; `P39=IF(C8<>1,U18,0)` | Excel COM: `Главная!H11→Z1!C8=4`, N40=2, N41=3. U10:U18 и P39 пересчитаны и сопоставлены для обеих книг |
| Активное стекло | `C9→'Прайс-Стекло'!D5:D16`; `H26:H28`; `H29=G26×H26+G27×H27+G28×H28`; `H33=H29+C23×W5`; `P40=IF(D32,H33,0)` | Одна рабочая ветвь с D32=1 подтверждена для каждого профиля |
| Цена конструкции | `P42=SUM(P38:P41)+IF(F28=2,C25×W5,0)`; `P44=SUM(P42:P43)`; `Sslot=P44/D12` | P38:P44 и S11/S12 проверены в шести валидных двухпозиционных заказах |

## Excel parity

`tools/jv/capture-zigzag-order-pr10g.ps1` пересчитывает временные копии обеих исходных книг через Excel 16 `CalculateFullRebuild`. Оригинальные XLSM не сохраняются и не меняются. Снимки входов, формул, Value2, IEEE-754, NumberFormat и отображения записаны в `docs/jv/fixtures/zigzag-order-pr10g-excel.json`. Проверяемый parity запускается командой `node --experimental-strip-types tools/jv/compare-zigzag-order-pr10g.mjs` и записывается в `docs/jv/ZIGZAG_ORDER_PR10G_PARITY.json`.

Захвачено 8 сценариев: два профиля × три валидных заказа (минимальные расходы, активные стекло и C8=4, расход до четырёх упаковок) + по одному случаю стекольной ошибки на профиль. Итого 16 расчётных позиций и 1 948 сравнений: **1 034 EXACT, 902 DISPLAY_MATCH, 0 NUMERICALLY_EQUIVALENT ячеечных сравнений, 0 MISMATCH, 12 UNVERIFIED**. Метки DISPLAY_MATCH означают совпавшее форматированное значение и не утверждают точное равенство неокруглённых чисел. Для агрегата по заказу 3 контрольных суммы дали точное двоичное равенство, ещё 3 совпали по отображению; ошибочные стекольные ветви не имеют числовой суммы и остаются UNVERIFIED.

В сценариях `4200×2500`, 5 створок, opening selector 3 при D32=1 Excel фактически возвращает `G23=-377.911111111111`, `H23="ОШИБКА"`, `C29="ОШИБКА"`, `H29=#VALUE!` (Value2 `-2146826273`) и `P40=#ЗНАЧ!`. Engine возвращает PARTIAL, фиксирует источник в trace/diagnostic, не подменяет P40 нулём и не выдаёт P42/P44/Sslot. Другая позиция такого заказа может быть рассчитана, но общий итог заказа не публикуется.

`docs/jv/ZIGZAG_ORDER_PR10G_PARITY.json` сохраняет 12 UNVERIFIED на downstream числовых ячейках этих двух Excel-error сценариев. Это ожидаемое отсутствие числа, а не расхождение: результат исходного Excel для P40 и итоговой цены сам является ошибкой.

## Покрытие и ограничения

- Одна и несколько Zigzag-позиций, несколько экземпляров, P38, P44, Sslot, обе ценовые книги и три valid commercial profiles покрыты.
- Ошибочная активная стекольная ветвь блокирует публикацию числового P40/P44 и переводит позицию/заказ в PARTIAL.
- Смешанные Line+Zigzag и другие семейства остаются PARTIAL: вклад другого семейства в общие N12/N25/O5/O18 не известен. Никакой общесистемный полный итог не публикуется.
- `/calculate`, legacy BMS, Prisma, база данных, React-интерфейс не менялись. Новый расчётный модуль доступен только из shared JV exports и не подключён к рабочему API.
