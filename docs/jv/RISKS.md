# Риски и расхождения

## P0
- Небезопасное выполнение формулы: BMS `apps/backend/src/lib/formulaEngine.ts:45` вызывает `new Function`. Новое ядро должно быть AST/интерпретатором закрытых операций; не подключать старое ядро как JV-движок.
- Excel semantics: каталог фиксирует IF, INDEX, AND, SUM, IFERROR, CONCATENATE, OR, ROUNDUP, ROUNDDOWN, ROUND, MAX, ISEVEN, CEILING, MATCH, TODAY. JavaScript round/ceil/floor и обычные массивы не дают полной Excel-семантики. Нужны тесты отрицательных половин и INDEX 1-based.
- Потеря ошибки: исключения в расчётных ветках обрабатываются локально, часть количеств/цен может стать 0 или 1 (`systems.ts:297–320`). Отличать inactive branch от ошибочной выбранной ветви.
- Формулы из `import-formulas.ts` сами помечены приблизительными; не использовать как oracle.

## P1
- Нет подтверждённого соответствия COMPLETATION/RETAIL и DEALER/PRIVATE. Ввести отдельный профиль цены.
- Расчёты компонентов, стекла, монтажа и dealExtras разнесены; риск пропуска/двойного начисления. Требуется единая итоговая сводка и trace.
- Нулевая настройка теряется в `dealExtras.ts:13` через `parseFloat(x)||default`.
- Значения Product/Setting/GlassType и действующих сделок не входят в archive/export; цены старых КП не воспроизводимы без версии и snapshot.
- SystemGlass отсутствует у систем в экспортном snapshot по интеграционному отчёту; требуется проверка кода/данных, не выводить это на живую БД.
- Product.unit — произвольная строка; нет размерно-типизированных количеств.

## P2
- Параметры Excel — не только формулы: validation/dropdowns/условия интерфейса нужно отразить в UX семантически.
- Две книги различаются минимум одним набором формул (по интеграционному отчёту — Настройки!E34) и различаются ценами/коэффициентами. Разность надо пересчитать/проверить, а не сводить к одному общему проценту.
- Кэши сохранены в XLSM, но openpyxl их извлекает без пересчёта; статус всех значений каталога `cached_unverified`.
