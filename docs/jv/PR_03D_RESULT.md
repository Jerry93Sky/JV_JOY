# PR_03D — JV-Line парковка и геометрия

## Итог

Реализованы три новых подтверждённых расчётных правила по формулам исходных книг: полная ветвящаяся логика D23, lookup-ветки O15 с исходными таблицами ПД и формула I25. Ранее реализованные I26 и I27 расширены/связаны с новыми правилами; повторно новыми правилами не считаются. Новая математика не включена в legacy `/calculate`.

| Реализованное правило | Исходный адрес и выражение Excel | Код |
|---|---|---|
| D23, состояние паркуемой двери | `L1!D23 = IF(C23,IF(D5/D6>1,"ДА","ОШИБКА"),"НЕТ")` | `geometry/line.ts`, `JV.LINE.PARKED_DOOR_STATE` |
| O15, детали/защёлки парковки | `L1!O15 = IF(D23="НЕТ",D6+2,0)+IF(AND(D23="ДА",D6=1),INDEX(ПД!D5:BA54,D5,C24),0)+IF(AND(D23="ДА",D6=2),INDEX(ПД!D61:BA110,D5,C24),0)` | `geometry/line.ts`, `JV.LINE.PARKING_PART_COUNT`; данные `geometry/pd-catalog.ts` |
| I25, ширина створки | `L1!I25 = ROUNDDOWN((D3-IF(C21,D6*D21,0)-2*P15-(D5-1)*P14-IF(D15="ДА",2*P4,0))/(D5-IF(C21,D6,0)),0)` | `geometry/line.ts`, `JV.LINE.OPENING_LEAF_WIDTH`; точное усечение реализует `divideDecimalTruncateToInteger` |
| I26, глубина парковки | `L1!I26 = P8+IF(D6=2,D5/2,D5)*P5+O15*P9+D22+P10` | `geometry/line.ts`, `JV.LINE.PARKING_DEPTH` (реализовано в предшествующем PR и расширено связью с PD) |
| I27, ширина по осям | `L1!I27 = I25-2*D22` | `geometry/line.ts`, `JV.LINE.PARKING_AXIS_WIDTH` (реализовано ранее, теперь включено в цепочку I25→I27) |

## Реестр ПД и точный lookup

Формулы O15 и массивы ПД проверены на обеих оригинальных книгах: `JV-комплектация 08.10.2026.xlsm` и `JV-розница 08.10.2026.xlsm`. Формулы D23/O15/I25/I26/I27 совпадают. Диапазоны `ПД!D5:BA54` и `ПД!D61:BA110` у книг совпадают по всем 5000 значениям. Каждый диапазон — 50×50, содержит только числовые константы, без пустых/формульных/ошибочных ячеек. Подробные контрольные хеши, отображение координат и граничные примеры находятся в [PD_LOOKUP_MAP.md](PD_LOOKUP_MAP.md).

Выбор ПД восстанавливается прямо из позиции `INDEX`: D5 — номер строки, C24 — номер столбца (1-based). При D6=1 берётся первый диапазон; при D6=2 — второй. Возвращённое значение содержит table ID/version, row/column index и точный адрес Excel (например `E6`/`E65`); та же информация сохраняется внутри результата trace для шага O15. Матрица не заменена вычисляемым приближением.

## D23 и Excel-ошибки

- `C23=false` лениво возвращает `НЕТ` и не вычисляет D5/D6 деление. Это отдельно проверено с D6=0; продолжение O15/I26 при допустимом числовом D6 остаётся независимым.
- `C23=true`: точное рациональное сравнение D5/D6>1 выполняется по знаку знаменателя без двоичного `Number` и без округления. Для положительного D6 это D5>D6; для отрицательного — D5<D6. Ноль даёт typed `DIVISION_BY_ZERO`.
- `ОШИБКА` является обычной строкой результата D23, не исключением. По условиям O15 при этой строке равен 0; I26 продолжает вычисление.
- Индексы больше 50/отрицательные дают typed `LOOKUP_NOT_FOUND` с Excel `#REF!`. Индекс 0 закрыт `RULE_UNCONFIRMED`, поскольку Excel `INDEX(...,0,...)` возвращает массив, а пересечение массива внутри O15 не подтверждено; дробные индексы также закрыты до подтверждения Excel-приведения. Ни один из этих случаев не заменяется нулём. Извлечённые исходные таблицы не содержат пустых/ошибочных значений; защита от повреждённого каталога предусмотрена, но такой исходный случай нельзя тестировать на оригинальных данных.
- При `D6` вне 1/2 D23 всё ещё может быть `ДА`; O15 не выбирает ни одну из матриц и суммирует нули согласно исходному выражению.

DAG сохраняет типизированные `EngineError`: `graph.ts` теперь не оборачивает доменные ошибки в общий `RULE_FAILED`. Другие исключения по-прежнему получают общий код ошибки правила.

## I25 → I27

I25 зависит от D3, D5, D6, C21, D21, D15 и настроек P4/P14/P15. Каждое условие сохранено: поправка D6×D21 применяется лишь при C21, рамный вычет 2×P4 — только при D15=`ДА`, межстворочный вычет — `(D5-1)×P14`, боковой — `2×P15`. `ROUNDDOWN(...,0)` выполнен точным делением десятичной дроби с усечением к нулю, включая отрицательное значение; политика округления не экстраполируется на другие формулы. I27 вычитает ровно `2×D22` из вычисленного I25.

На уровне BMS подтверждено только частичное соответствие входов: legacy `apps/backend/src/prisma/import-excel.ts` описывает `width`, `height`, `panels`, `hasSide`; параметр C23/C24 и точные исходные настройки P4/P14/P15/P5/P8/P9/P10 из этого описания однозначно не сопоставляются. Legacy `apps/backend/src/prisma/import-formulas.ts` содержит упрощённые формулы комплектующих; PR_03D их не меняет и не использует как источник новых правил. Ячейки настроек в книгах не подписаны единицами измерения; API требует явную общую единицу от вызывающего кода и не утверждает, что это mm.

## Цепочки и геометрические выходы

Замкнуты четыре рабочих расчётных цепочки:

1. C23=false → D23=`НЕТ` → O15=D6+2 → I26.
2. C23=true, D6=1, D5/D6>1 → D23=`ДА` → первый PD INDEX → O15 → I26.
3. C23=true, D6=2, D5/D6>1 → D23=`ДА` → второй PD INDEX → O15 → I26.
4. D3/D5/D6/C21/D21/D15/P4/P14/P15 → I25 → I27.

Ветка D23=`ОШИБКА` также полностью считается как формульная строка и продолжает через O15=0/I26; она учтена как ветвь ошибки Excel, а не как пятая самостоятельная геометрическая цепочка. Результаты доступны как структурированные значения с явной входной единицей, статусом `EXCEL_PARITY_UNVERIFIED` и DAG-trace. В I26 result parking table lookup carries table provenance. Новые числовые тесты — ручные независимые вычисления по опубликованным выражениям и исходным ячейкам, не эталоны пересчёта Excel.

## Ограничения и следующие блоки

- Сравнения с формулами подтверждены статическим извлечением, но числовые Excel golden outputs не получены: расчётный Excel не запускался, сохранённый кэш эталоном не является.
- Текстовый D6=`НЕТ` (из исходной формулы D6 при числе сторон >2) поддержан как вход: D23 с C23=false остаётся ленивым, а последующее сложение D6+2 в O15 возвращает typed `INVALID_DECIMAL` с Excel `#VALUE!`; при C23=true деление на текст тоже даёт этот типизированный эквивалент. Поведение заранее присутствующих Excel-значений типа error/blank и совместимость принудительного пересечения массивов остаются за пределами API.
- Физические единицы и однозначное соответствие полей формы BMS входам L1 ещё не подтверждены.
- Не перенесены следующие связанные формулы раскроя `L1!C28:D32`, профильные настройки P2/P6/P7 и downstream BOM. Эти адреса — следующий непосредственный расчётный блок JV-Line.

**Результат PR_03D:** 3 новых правила, 4 рабочих цепочки (плюс проверенная строковая ветвь D23=`ОШИБКА`), 8 новых тестов, 18/18 тестов пройдены. Расчётная сверка с пересчитанным Excel остаётся непроверенной.
